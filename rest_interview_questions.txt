TOP 10 REST INTERVIEW QUESTIONS AND ANSWERS
=============================================

1. What is REST, and what makes an API "RESTful"?

REST (Representational State Transfer) is an architectural style for
distributed systems, defined by Roy Fielding in his 2000 dissertation.
It's not a protocol or standard -- it's a set of constraints:

- Client-server -- separation of concerns; UI and data storage evolve
  independently.
- Statelessness -- each request contains all information needed to
  process it; the server holds no client session state between requests.
- Cacheability -- responses must define themselves as cacheable or not.
- Uniform interface -- the core constraint (see Q2).
- Layered system -- client can't tell if it's talking directly to the
  server or through intermediaries (proxies, load balancers).
- Code on demand (optional) -- server can extend client functionality by
  sending executable code (e.g., JavaScript).

An API is "RESTful" if it honors these constraints, particularly
statelessness and the uniform interface -- many APIs called "REST" are
really just HTTP+JSON APIs that violate statelessness (e.g., relying on
server-side sessions).


2. What is the "uniform interface" constraint, and what are its four
   sub-constraints?

This is the constraint that most distinguishes REST from other
architectures:

- Resource identification in requests -- resources are identified by URIs
  (e.g., /users/42), not by an RPC-style method name.
- Manipulation of resources through representations -- a client holding a
  representation (JSON/XML) has enough information to modify or delete
  the resource.
- Self-descriptive messages -- each message includes enough info to
  process it (e.g., Content-Type: application/json), independent of prior
  messages.
- HATEOAS (Hypermedia as the Engine of Application State) -- responses
  include links to related actions/resources, so clients navigate the API
  dynamically rather than hardcoding URLs. This is the constraint almost
  everyone skips in practice.


3. What's the difference between PUT, POST, and PATCH?

- POST -- creates a new resource; not idempotent (calling it twice
  creates two resources). Used when the server assigns the resource's
  identity.
- PUT -- replaces a resource entirely at a known URI; idempotent (calling
  it N times has the same effect as calling it once). Client specifies
  the full resource state.
- PATCH -- partially updates a resource; not required to be idempotent
  (though can be), only sends the fields that changed.

Example:
    POST /users          -> create a new user, server assigns id
    PUT /users/42         -> replace user 42 entirely with the given body
    PATCH /users/42       -> update only the fields provided (e.g.,
                             {"email": "..."})


4. What does "idempotent" mean, and which HTTP methods are idempotent?

An operation is idempotent if performing it multiple times produces the
same result as performing it once (same end state, though the response
may differ, e.g., a 404 on the second DELETE).

- Idempotent: GET, PUT, DELETE, HEAD, OPTIONS.
- Not idempotent: POST, PATCH (though PATCH CAN be designed to be
  idempotent).

This matters for retry logic -- clients/proxies can safely retry
idempotent requests after a timeout without risking duplicate side
effects (e.g., double-charging a customer), but retrying a POST blindly
can cause duplicate resource creation.


5. What's the difference between authentication and authorization in a
   REST API, and how are they typically implemented?

- Authentication -- verifying WHO the caller is (e.g., API keys, OAuth2
  bearer tokens, JWTs, Basic Auth).
- Authorization -- verifying WHAT the authenticated caller is allowed to
  do (e.g., RBAC checks, scopes on an OAuth token).

Because REST is stateless, authentication info (a token) must be sent
with EVERY request -- typically via the Authorization: Bearer <token>
header -- rather than relying on a server-side session cookie. JWTs are
popular because they're self-contained (claims + signature), letting the
server validate them without a database lookup, at the cost of harder
revocation.


6. What status codes should a REST API return, and when?

Know the categories and the commonly-tested specifics:

- 2xx Success -- 200 OK (general success), 201 Created (POST that created
  a resource -- should include a Location header), 204 No Content
  (success with no body, e.g., DELETE).
- 3xx Redirection -- 301 Moved Permanently, 304 Not Modified (caching).
- 4xx Client Error -- 400 Bad Request (malformed input), 401 Unauthorized
  (not authenticated), 403 Forbidden (authenticated but not allowed), 404
  Not Found, 409 Conflict (e.g., version mismatch), 422 Unprocessable
  Entity (semantically invalid, e.g., failed validation).
- 5xx Server Error -- 500 Internal Server Error, 503 Service Unavailable.

Common interview trap: distinguishing 401 (who are you?) from 403 (I know
who you are, but no).


7. How should a REST API handle versioning?

There's no single "correct" answer -- this question tests whether you
know the tradeoffs:

- URI versioning -- /v1/users -- simple, visible, but "pollutes" the URI
  (arguably violates REST's idea that a URI identifies a resource, not a
  version of it).
- Header versioning -- Accept: application/vnd.myapi.v1+json -- keeps
  URIs clean, more RESTful in spirit, but harder to test in a
  browser/curl casually.
- Query parameter -- /users?version=1 -- easy but easy to omit
  accidentally, less common in practice.

Most real-world APIs (Stripe, GitHub) use URI or header versioning; the
key point is picking one and being consistent, and having a deprecation
policy.


8. What is HATEOAS, and why do so few "REST" APIs actually implement it?

HATEOAS means a client interacts with an API entirely through hypermedia
links provided dynamically by the server in responses, rather than
hardcoding endpoint URLs based on out-of-band documentation.

Example:
    {
      "id": 42,
      "status": "pending",
      "_links": {
        "self": { "href": "/orders/42" },
        "cancel": { "href": "/orders/42/cancel" }
      }
    }

In theory, this decouples clients from the server's URL structure (like a
browser following <a> tags rather than hardcoding site navigation) and
lets the API evolve without breaking clients. In practice, it's rarely
implemented because: it adds real complexity, most internal/first-party
API consumers don't need this level of decoupling, and tooling
(OpenAPI/Swagger-generated clients) assumes fixed known endpoints anyway.
This is why many say "most REST APIs are not actually REST, they're just
HTTP APIs" -- Fielding himself has made this complaint.


9. How do you handle pagination, filtering, and sorting in a REST API?

- Pagination:
  - Offset-based -- ?page=2&limit=20 or ?offset=40&limit=20 -- simple,
    but unstable if rows are inserted/deleted between requests (items can
    shift, causing skips/duplicates).
  - Cursor-based -- ?after=eyJpZCI6NDJ9 -- uses an opaque pointer (often
    an encoded last-seen ID), stable under concurrent writes, standard
    for large/real-time datasets (used by Twitter, Stripe, GitHub's
    GraphQL API).
- Filtering: query params matching field names, e.g.,
  ?status=active&created_after=2026-01-01.
- Sorting: a sort param, e.g., ?sort=-created_at,name (- prefix for
  descending).

Good answers mention that pagination metadata (total count, next/prev
links) is often returned in the body or in Link headers (GitHub's API
does the latter).


10. REST vs GraphQL vs gRPC -- when would you choose each?

- REST -- resource-oriented, cacheable via HTTP semantics, simple mental
  model, wide tooling support, but prone to over-fetching (getting fields
  you don't need) or under-fetching (needing multiple round trips for
  related resources, i.e., the N+1 problem).
- GraphQL -- client specifies exactly the fields/nested relations it
  needs in one request, solving over/under-fetching, but loses HTTP-level
  caching (typically single POST /graphql endpoint), and shifts
  complexity to query resolution/N+1 on the server side (needs
  DataLoader-style batching).
- gRPC -- binary protocol (Protocol Buffers) over HTTP/2, built for
  low-latency service-to-service (internal microservices) communication
  with strongly-typed contracts and streaming support; not browser-
  friendly without a proxy (grpc-web), and not human-readable on the wire
  like JSON.

Good answer signals judgment: REST for public-facing/simple CRUD APIs,
GraphQL for complex/nested client-driven data needs (mobile apps
aggregating many resources), gRPC for internal high-performance service
communication.
